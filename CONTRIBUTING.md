# Contributing to the Ultra Sprint

The Ultra Sprint is a living method. If you've run a sprint and found something that could be improved, or if you spot a gap in the guide, contributions are welcome.

---

## Ways to contribute

### Share your experience

The most valuable contributions come from people who have actually run an Ultra Sprint. If you did, open an issue titled something like "Sprint report: [your context]" and share what worked, what didn't, and what you changed. Even if you don't have a specific fix in mind, these reports help shape future versions of the method.

### Suggest a change

If you have a specific improvement in mind, open an issue describing the change you'd propose, the reason behind it, and - if applicable - how it went when you tested it. Clear reasoning matters more than length.

### Submit a pull request

If you'd like to propose an edit directly, submit a pull request against `ULTRA-SPRINT-GUIDE.md` (or any other file that needs updating). In your PR description, include what you changed, why you changed it, and whether you've tested it in a real sprint.

Small fixes (typos, unclear phrasing, broken links) don't need a sprint report - just submit them.

### Fork and build your own variant

The Ultra Sprint is licensed under CC BY 4.0, so you're free to fork and adapt it however you like. If you build a significantly different variant, consider linking back to this repository so others can find the original.

---

## Guidelines

**Test before you propose.** For structural changes (adding a phase, removing a phase, changing timings, changing team size), we strongly prefer proposals that have been tested in at least one real sprint. Untested ideas are welcome as issues for discussion, but are unlikely to be merged directly.

**Describe the why, not just the what.** A good contribution explains the problem it solves or the situation it addresses. "We shortened the blueprint phase to 20 minutes because our team of 3 consistently finished early" is more useful than "Changed blueprint to 20 min."

**Keep the guide's tone.** The Ultra Sprint guide is written to be practical and direct. If you're editing text, try to match the existing tone: clear instructions, no jargon, concrete rather than abstract.

**One change per PR.** If you have multiple unrelated suggestions, submit them as separate pull requests. This makes each one easier to review and discuss.

**Changelog convention.** If your change is significant enough to note in the changelog, add an entry describing what changed and why - not just that it changed.

---

## What belongs in an issue vs. a pull request

Open an **issue** when you want to start a discussion, share a sprint report, ask whether a change makes sense, or flag a problem without a clear fix yet.

Open a **pull request** when you have a specific, concrete edit ready to review.

When in doubt, start with an issue.
